# AI 能力评估与选型工作台（AI Sizing & Evaluation Workbench）

> 输入业务场景参数，输出一套可直接进评审会的三件套：**技术选型评估报告 + PRD 初稿 + 产品路线图**。
>
> **场景为自拟、结论为方法论验证，非真实业务项目。** 全部成本数字来自公开单价表离线测算，
> 不调用任何付费 API。

零第三方依赖，`git clone` 后直接跑。

---

## 1. 为什么做这个

AI 落地的常见失败不是模型不够强，而是**选错了技术路线**：

- 明明是关系型问题（"A 制度与 B 制度什么关系"），却上了向量检索，召回一堆相似文本却答不上来；
- 明明只是格式输出问题，却上了知识图谱，工程复杂度翻三倍；
- 方案上线后没人知道效果是好是坏，因为**没有可复现的评估基线**。

更麻烦的是：选型结论通常只在会议纪要里留一句"决定用 RAG"，
半年后就没人说得清当时的依据，也没人能复现。

这个工具做的事是：**把"为什么选这条路线"变成可复现、可追问、可推翻的流程**。

它输出的是**倾向 + 置信度 + 依据 + 排除理由**，不是唯一正确答案。
选型不是选最好的，是选当前约束下代价最小的 —— 换约束，结论可能反转。

## 2. 覆盖哪些问题

| 能力 | 输入 | 输出 | 关键约束 |
|---|---|---|---|
| 技术路线判定 | 场景特征四维 | 四档路线之一 + 置信度 + 依据 | 每条判定必须有规则编号；判不出时返回 `insufficient_data` 而非硬凑 |
| 能力测算 | 语料规模 + 流量 | 向量规模、Token 预算、各模型月度成本 | 成本按峰谷混合单价算，**不含任何商务折扣** |
| 效果评估 | 标注样本 + 语料 | Recall / Precision / 拒答率 | **算不出的指标一律标「未查到」，不填估计值** |
| PRD 装配 | 以上全部 | 7 章 PRD 初稿 | 目标必须有衡量口径；未达标处显式标注 |
| 路线图 | 阶段划分 | 4 阶段 + 退出标准 | 按**退出标准**而非时间推进 |
| PRD 自评 | 生成结果 | 13 项评分 + 扣分原因 | **工具评自己的产出**，低分说明工具本身有缺陷 |

**四维场景特征 → 技术路线**（这是本项目的核心判断逻辑）：

| 特征 | 命中规则 | 倾向路线 |
|---|---|---|
| 有语料 + 要求事实准确 | R-01 | RAG |
| 需要跨域推理 | R-02 | 知识图谱 |
| 无语料 + 长篇结构化输出 | R-03 | 模型微调 |
| 无语料 + 不需推理 + 短事实 | R-04 | 纯提示词 |

同时命中多条时按优先级裁决，**并显式写出被排除的路线与排除理由** ——
"为什么不选另外三条"比"为什么选这一条"更能体现判断力。

## 3. 数据源与合规边界

| 数据 | 来源 | 说明 |
|---|---|---|
| 模型上下文长度 / 单价 / 峰谷倍率 | DeepSeek API 官方定价文档 | 每行带 `source_id` 与 `credibility` |
| 场景参数 | `data/scenarios/*.json` | **自拟**，非真实客户需求 |
| 评估样本 | `data/benchmarks/qa_eval_samples.json` | 自拟标注，10 条 |
| 语料 | `data/corpus/*.json` | 自拟文档，**显式提供以保证可复现** |
| 假设 | `data/assumptions.md` | A-01~A-06 逐条登记依据 |

**明确不含**：真实客户名称、合同金额、账号凭据、内部报价、客户业务数据。

### 一个容易算错的地方：峰谷分时

DeepSeek 自 2026-08-16 起实行峰谷分时计费，峰时（UTC 01–04、06–10）单价翻倍。
本项目按峰时占比折算混合单价：

```text
混合单价 = 谷时价 × (1 + 峰时占比 × (峰时倍率 − 1))
```

峰时占比登记为 A-05，取值 0.30，**标注为「占位待实测替换」** ——
真实值须用调用日志统计。`data/models.csv` 同时保留原始谷时价与倍率，改占比不用改价目表。

## 4. 方法

```
data/scenarios/<场景>.json ──> router.decide ──────> 路线 + 置信度 + 依据 + 排除理由
data/models.csv ─────────────> sizing.size ───────> 向量规模 + Token 预算 + 月度成本
data/corpus/<场景>_corpus.json ──> corpus.build_corpus ──> chunks
data/benchmarks/qa_eval_samples.json ──> evaluator.evaluate ──> 5 项指标
                                       │
                     report_builder ────┴──> 评估报告 + PRD 初稿 + 路线图
scorecard.score_prd ────────────────────────> 13 项质量自评 + 扣分原因
```

三条设计取舍：

1. **检索器抽成独立模块**（`src/retriever.py`）。当前是确定性 token 重叠实现，
   换成真实向量检索只需替换 `retrieve()`，评估逻辑不动。
2. **文档级而非 chunk 级召回**。chunk 边界由切分参数决定，把标注硬绑到 chunk 上
   换个切分参数就全失效；标注到 doc 级更稳定，也更接近"该问题该由哪份文档回答"的真实语义。
3. **评分卡评自己的产出**。一个会生成文档的工具必须能判断自己生成的够不够格。

## 5. 快速开始

环境：Python 3.10+（验证于 3.12.8 / Windows）。**无需安装任何运行时依赖。**

```bash
# 列出可用场景
python -m src.cli --list

# 生成单个场景的三件套
python -m src.cli --scenario customer_service

# 一次生成全部场景
python -m src.cli --all

# 生成后对 PRD 打分并列出扣分项
python -m src.cli --all --selfcheck

# 跑测试
pip install pytest
python -m pytest -q
```

输出落在 `output/<场景编号>/`：

| 文件 | 内容 |
|---|---|
| `evaluation_report.md` | 评估报告：结论摘要、路线判定与依据、能力测算、评估结果、边界声明 |
| `prd_draft.md` | PRD 初稿：背景目标、用户场景、方案选型、非功能需求、评估验收、迭代计划、待明确事项 |
| `roadmap.md` | 4 阶段路线图，每阶段带退出标准 |
| `model_costs.csv` | 各模型月度/年度成本与相对倍数 |
| `result.json` | 全量结构化结果 |

```text
$ python -m pytest -q
.......................................................                  [100%]
55 passed in 0.69s

$ python -m src.cli --all --selfcheck
PRD 质量自评：98 / 98
  [OK  ] 含业务背景且非空
  [OK  ] 含可量化目标
  [OK  ] 未达标指标标注为未查到
  [OK  ] 技术路线有明确结论
  [OK  ] 技术路线给出依据条目
  [OK  ] 给出置信度而非绝对结论
  [OK  ] 含被排除方案及理由
  [OK  ] 含非功能需求
  [OK  ] 含评估指标与口径
  [OK  ] 含阶段化迭代计划
  [OK  ] 路线图有退出标准
  [OK  ] 至少一项评估指标为实测值
  [OK  ] 成本测算含全部候选模型
```

三个场景的判定结果（同一套规则，不同场景特征得出不同结论）：

| 场景 | 语料 | 需事实准确 | 需跨域推理 | 输出形态 | 结论 | 置信度 |
|---|---|---|---|---|---|---|
| 电商客服知识问答 | 1200 篇 | 是 | 否 | 短事实 | RAG | high |
| 集团制度与流程知识问答 | 8600 篇 | 是 | 是 | 长推理 | 知识图谱 | medium |
| 经营周报与报告生成 | 150 篇 | 否 | 是 | 长推理 | 知识图谱 | high |

两个场景同为知识图谱但置信度不同，差别在语料：
`enterprise_knowledge_qa` 的 8600 篇语料同时满足 RAG 规则（R-01）与图谱规则（R-02），
两条候选竞争 → 按优先级选图谱，置信度降为 **medium**；
`report_generation` 只有 150 篇且不要求事实准确，R-01 不成立 → 只有图谱一条候选 → **high**。

`enterprise_knowledge_qa` 的 medium 会在报告里写明：
"结论取决于更看重关系推理还是更看重检索召回，需业务方拍板" ——
**这个不确定度是决策风险信号，必须如实暴露而不是藏起来。**

顺带说明一个反直觉的判定：`report_generation` 明明只需"按模板写周报"，
却判成知识图谱而非微调。原因是它有 150 篇语料且要求跨域推理，
R-02 命中；而微调规则 R-03 要求 `corpus_docs == 0`，此处不成立。
**这说明规则优先级本身就是一种产品判断** —— 换掉 R-02/R-03 的优先级，结论会变。
这也是输出里必须带规则编号的原因：让评审能质疑规则，而不只是质疑结论。

## 7. 已知局限

| # | 局限 | 影响 | 补齐方式 |
|---|---|---|---|
| 1 | **检索器是模拟实现** | 评估指标用于验证流程可复现，**不代表真实检索质量** | 替换 `src/retriever.py::retrieve()` 为真实向量检索 |
| 2 | **不实测延迟** | P50/P95 恒为「未查到」 | 接入推理环境后按「检索 + 生成」两段分别测量 |
| 3 | **无生成环节** | 答案正确率无法自动计算 | 需人工标注或接入生成模型 |
| 4 | 语料与场景均为自拟 | 结论不代表任何真实业务特征 | 拿到真实需求后替换 JSON 重跑，代码无需改动 |
| 5 | 峰时占比为占位值 | 混合单价有偏差 | 用真实调用日志统计峰时占比 |
| 6 | 模型候选仅 2 个 | 选型讨论覆盖面有限 | 在 `data/models.csv` 增行即可，无需改代码 |
| 7 | 不含微调超参设计 | 只判断"是否需要微调" | 微调方案需单独设计 |

第 1、2、3 条是本项目最大的短板，明确写在这里而不是藏起来：
**这个工具验证的是"选型判断方法与评估流程是否站得住"，不是"某个模型的真实效果"。**
前者现在就能做，后者必须等真实环境。
